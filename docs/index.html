Setting up the architecture gate in your CI

How a team with a real C# repository stops architecture violations from merging — on GitHub Actions, GitLab, Azure DevOps, or anything that can run a container. Section 4 is the one that decides whether the rollout survives contact with a codebase that already has violations.

01Pick your path

Four channels. They compose rather than compete — most teams end up with the analyzer package for fast local feedback and the Action for the gate.

You wantUseEffort
Violations to fail the build everywhere, including on developers' machines Portcullis.Analyzers package one line
A pull-request gate with a comment, on GitHub The Action one workflow file
The same on GitLab, Azure DevOps or Jenkins portcullis tool, or the container a few lines
To look before committing to anything portcullis scan locally one command

The analyzer catches a violation before you push; the gate catches it if you push anyway. Neither replaces the other.

02The fast path: the analyzer package

One package reference. No CI step, nothing installed on the runner.

dotnet add package Portcullis.Analyzers

On the next dotnet build, violations arrive as ordinary compiler diagnostics — which means they work in Visual Studio, Rider, VS Code, dotnet build, and every CI system that already builds your code:

Verified: this exact output, from a throwaway project that never referenced the Portcullis source.

To cover every project at once, put it in Directory.Build.props:

<Project>
  <ItemGroup>
    <PackageReference Include="Portcullis.Analyzers" Version="0.1.0" PrivateAssets="all" />
  </ItemGroup>
</Project>

PrivateAssets="all" stops Portcullis appearing as a dependency of your package if you publish one. Pin the version — Version="*" means a rule added in a later release can fail your build with nobody having changed a line.

One limitation

This path has no diff scoping: every violation in every file is reported on every build. Correct for a compiler diagnostic, wrong for a first encounter with a legacy codebase — see §4.

03The pull-request gate

GitHub Actions

A complete, working gate: scans src/, posts one sticky comment that updates in place instead of spamming a new one per push, and fails the job when the gate blocks.

# .github/workflows/architecture.yml
name: Architecture
on: pull_request

permissions:
  contents: read
  pull-requests: write        # required for the sticky comment

jobs:
  portcullis:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0      # required — see below
      - uses: konradcinkusz/letsgolegacy.portcullis@v0
        with:
          path: src
fetch-depth: 0 is not optional

actions/checkout defaults to a shallow clone that does not contain your PR's base commit. Without it Portcullis cannot tell which lines your PR changed, so diff scoping silently cannot happen. The Action detects this, prints a warning, and falls back to whole-tree scope — it does not pretend to have scoped when it hasn't. But the fix is this line, not the warning.

InputDefaultWhat it does
pathsrcDirectory to scan, relative to the repo root
versionpinnedVersion of the tools to install
diff-scopedtrueOnly violations in the PR's own changed lines can block
commenttruePost / update the sticky PR comment
fail-on-blocktrueSet false to report without enforcing
github-tokengithub.tokenToken that publishes the sticky comment; needs pull-requests: write
dotnet-version10.0.xSet '' to use the runner's existing SDK

Outputs — blocked, error-count, blocking-error-count, gate-scope (diff or all: which lines could block) and result-path — let a later step react:

- uses: konradcinkusz/letsgolegacy.portcullis@v0
  id: portcullis
  with: { path: src, fail-on-block: false }
- if: steps.portcullis.outputs.blocked == 'true'
  run: echo "would block on ${{ steps.portcullis.outputs.blocking-error-count }} violation(s)"

GitLab CI

The container needs no .NET SDK on the runner. One wrinkle: GitLab overrides a container's ENTRYPOINT, so call the DLL explicitly.

portcullis:
  image: ghcr.io/konradcinkusz/letsgolegacy.portcullis:0.1.0
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
  variables:
    GIT_DEPTH: 0              # same reason as fetch-depth: 0
  script:
    - dotnet /app/Portcullis.Cli.dll scan "$CI_PROJECT_DIR/src"
        --provenance-range "$CI_MERGE_REQUEST_DIFF_BASE_SHA..$CI_COMMIT_SHA"
        --provenance-repo "$CI_PROJECT_DIR"
        | tee portcullis.json
  artifacts:
    when: always
    paths: [portcullis.json]

Azure DevOps

- task: UseDotNet@2
  inputs: { version: '10.0.x' }

- script: |
    dotnet tool install -g Portcullis.Cli --version 0.1.0
    export PATH="$PATH:$HOME/.dotnet/tools"
    BASE=$(git merge-base "origin/$(System.PullRequest.TargetBranch)" HEAD)
    portcullis scan "$(Build.SourcesDirectory)/src" \
      --provenance-range "$BASE..HEAD" \
      --provenance-repo "$(Build.SourcesDirectory)"
  displayName: Portcullis

Anything else

The portable form — git merge-base works everywhere and needs no CI-specific variables:

BASE=$(git merge-base origin/main HEAD)
portcullis scan ./src --provenance-range "$BASE..HEAD" --provenance-repo .

# or with no .NET installed at all
docker run --rm -v "$PWD:/workspace" ghcr.io/konradcinkusz/letsgolegacy.portcullis:0.1.0 \
  scan /workspace/src --provenance-range "$BASE..HEAD" --provenance-repo /workspace

04Adopting on a codebase that already has violations

This is where most architecture-gate rollouts die. It is worth the five minutes.

Point any rule engine at a real codebase and it finds pre-existing violations — that is the point of it. But a gate that fails on all of them fails every pull request, including one-line changes touching nothing related. Developers can't merge, so within a week somebody switches the gate off, and it never comes back on.

Portcullis has three independent answers, and they compose.

4.1  Diff scoping — on by default in the Action

Given a commit range, Portcullis still reports every violation it finds, but only blocks on ones inside the lines your PR actually changed. A real run against a repository carrying pre-existing errors, where the PR changed one unrelated file:

And the PR comment says so plainly rather than leaving anyone to guess:

ℹ️ Not blocking this PR — the 1 error above is outside this PR's own changed lines.

The effect: existing debt stays visible on every PR without being anyone's emergency, while anything new is stopped at the boundary. Debt shrinks as files get touched, instead of demanding a big-bang cleanup before the gate can be switched on at all.

4.2  Severity ratcheting via .editorconfig

Every rule is an ordinary Roslyn diagnostic, so it tunes the ordinary way — per rule, and per path:

# .editorconfig
root = true

[*.cs]
# start noisy rules as suggestions while you pay down violations
dotnet_diagnostic.PORTCULLIS_P10_CUSTOM_BASE_CLASS.severity = suggestion

# turn one all the way off for now
dotnet_diagnostic.PORTCULLIS_P4_SEED_DATA_IN_MODEL.severity = none

# promote one you're already clean on, so it can never regress
dotnet_diagnostic.PORTCULLIS_P9_ORPHAN_ENTITY.severity = error

# legacy code is exempt; new code is not
[src/Legacy/**.cs]
dotnet_diagnostic.PORTCULLIS_P9_CONTROLLER_NO_DBCONTEXT.severity = none

Verified, not assumed: promoting PORTCULLIS_P9_ORPHAN_ENTITY to error failed a build that previously passed; setting PORTCULLIS_P9_CONTROLLER_NO_DBCONTEXT to none removed a build-failing error entirely.

A sane rollout

Everything to suggestion on day one → fix one rule's violations → raise that rule to warning, then error → repeat. Each ratchet is one line, and no step ever blocks work unrelated to it.

4.3  A baseline file

Record the findings that exist today, once, and commit the file:

portcullis scan ./src --baseline portcullis-baseline.json --write-baseline

From then on, pass --baseline portcullis-baseline.json to every scan. A finding the file accepts is still reported — marked (accepted by the baseline) in the PR comment — but it never blocks, even on a line the pull request touched. Findings are matched by a fingerprint of rule, file and line text, not by line number, so edits elsewhere and re-indentation leave accepted debt accepted; rewriting the line makes it new again. Details, and SARIF output for code scanning, in SARIF.md.

05Reading the output

portcullis scan prints one JSON document per run.

{
  "filesScanned": 156,
  "rulesEvaluated": 11,
  "violations": [
    { "ruleId": "PORTCULLIS_P9_ORPHAN_ENTITY", "filePath": "Domain/QrCode.cs",
      "line": 11, "message": "...", "severity": "warning" }
  ],
  "summary": { "errorCount": 9, "warningCount": 9, "infoCount": 0 },
  "gate": { "blocked": true, "scope": "diff", "blockingErrorCount": 5 }
}

summary is what was found. gate is what blocks. They are deliberately different numbers, and the gap between them is your pre-existing debt.

Exit codeMeaning
0Not blocked
1Blocked — a verdict, not a failure
2Bad usage — the only code that means Portcullis itself failed

06Troubleshooting

Built from real failure modes, not imagined ones.

SymptomCause and fix
gate.scope is "all" when you expected "diff" The base commit isn't in the checkout. Add fetch-depth: 0 (GitHub) or GIT_DEPTH: 0 (GitLab).
Gate passes when you're sure it should block Check gate.scope. If it is "diff", the violation is outside this PR's own changed lines — the gate working as designed. If it is "all" with a degradedReason, git could not resolve your range and the scan fell back to whole-tree gating; the reason says what failed. A git failure no longer passes silently — see DIFF-GATE.md §3.
Package installs but no diagnostics ever appear Check the DLL sits at analyzers/dotnet/cs/ inside the .nupkg. An analyzer packed to lib/ installs cleanly and does nothing at all.
warning CS9057: … references version 4.x of the compiler, which is newer Your SDK's Roslyn is older than the one Portcullis was built against. The package targets Roslyn 4.8 (the .NET 8 SDK's version) precisely to avoid this — seeing it means you're on an older SDK than .NET 8.
docker pull from GHCR says unauthorized A GHCR package is created private on its first push regardless of repository visibility. It has to be made public once, in the package's own settings.
Rules don't fire on code you know is wrong Portcullis parses source directly rather than through MSBuild, so a type from a NuGet package or another project doesn't resolve. Some rules depend on that; others are blunted by it.
A rule fires on code that is correct That's a bug worth reporting, not something to work around — a noisy gate is worse than a missing rule. Silence it per §4.2 and open an issue with the snippet.

07Before the first release: running from source

Works today. Needs only the .NET 10 SDK.

git clone https://github.com/konradcinkusz/letsgolegacy.portcullis
cd letsgolegacy.portcullis
dotnet build portcullis.sln

# scan any repository on your machine
dotnet run --project src/Portcullis.Cli -- scan /path/to/your-repo/src

# with the diff-scoped gate
cd /path/to/your-repo
BASE=$(git merge-base origin/main HEAD)
dotnet run --project /path/to/letsgolegacy.portcullis/src/Portcullis.Cli -- \
  scan ./src --provenance-range "$BASE..HEAD" --provenance-repo .

You can also build the analyzer package locally and consume it from a private feed:

dotnet pack src/Portcullis.Rules/Portcullis.Rules.csproj -c Release -o ./artifacts
# then add ./artifacts as a package source in your repo's nuget.config

08What it can't do yet

Stated here rather than discovered later.

  • Rule shape is fixed even though the conventions are configurable. You can tell a rule where your adapters live (see docs/CONFIGURATION.md); you cannot redefine what counts as leaking a vendor type.
  • Six of fifteen principles. Nine are unimplemented — five need cross-file or temporal judgment a single-snapshot analyzer doesn't have, four aren't C# at all (Dockerfiles, fly.toml, CI YAML, prose).
  • The container image and release workflow are unexecuted. Both need a real tag push; the distribution notes say so rather than claiming they work.
  • A git failure degrades the gate rather than passing it — the scan falls back to whole-tree gating and reports gate.degradedReason, as in §6.

If something here doesn't work as written, that's a documentation bug worth an issue — every command in this guide except the container examples was run before it was written down.
